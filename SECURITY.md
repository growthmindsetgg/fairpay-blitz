# Security model

**Audit status: unaudited.** None of the contracts, the SDK, the FairEats server or the FairPay app has had an independent audit. Do not hold meaningful funds in FairPool until they have. Keep `maxDeposits` low and the owner key in a Safe or hardware wallet. Everything in this repository runs on Monad Testnet with a mintable MockUSDC.

## What each party sees

| | Public payment | Private payment |
|---|---|---|
| Customer wallet | Public | Visible at **deposit** only, not in the payment transaction |
| Merchant | Public | Public |
| Amount | Public | Public (fixed denomination) |
| Order | Opaque `orderRef` only | Opaque `orderRef` only |
| Link deposit → payment | n/a | Hidden by a zero-knowledge proof among the deposits in the tree the proof used |

This is privacy from the public chain. It is not privacy from the restaurant's server, the RPC provider or anyone watching the network: see [Known limitations](#known-limitations).

## Guarantees and how they are enforced

| Guarantee | Mechanism | Test |
|---|---|---|
| A note is spent once | Pool-local nullifier set, set before calling out; scope pinned to `SCOPE` so one identity has exactly one nullifier | `FairPool.test.ts` double-spend, wrong-scope |
| A payment cannot be redirected | Proof message = `keccak256(merchant, orderRef)`. A front-runner who copies a proof still pays the same merchant for the same order | redirect test, front-run test |
| No nullifier aliasing | Verifier rejects signals ≥ field modulus | `nullifier + p` test |
| No griefing through a shared Semaphore | Pool keeps its own tree and nullifiers; nothing else can spend them | design (see `FairPool.sol` header) |
| Proofs not replayable across chains/pools | `SCOPE` = hash(chain id, pool address, denomination) | wrong-scope test |
| Pool stays solvent | Exact-amount deposits, balance-delta checks | solvency test |
| Owner cannot take pooled funds | No such function exists | code review |
| Users can always take a note back | `withdraw(recipient, proof)` sends `DENOMINATION` to any recipient; it is not `whenNotPaused` and ignores the allowlist, so pausing, delisting or renouncing ownership cannot freeze notes | `FairPool.test.ts` withdraw tests (incl. paused, no merchants, renounced) |
| A withdrawal cannot be redirected | Proof message = `withdrawMessage(recipient)` = `keccak256(recipient, WITHDRAW_REF)`. A relayer or front-runner who copies the proof can only send the money to the same recipient. `pay` and `withdraw` share the nullifier set, so a note is spent once by either | withdraw redirect, reuse and cross-path tests |
| Event amount = amount received | Balance-delta check rejects fee-on-transfer tokens | fee-token test |
| The pool cannot be faked as payer | `FairPay` sets `payer = msg.sender` | code review |
| Merchant trusts only the chain | `verifyPaymentTx` checks receipt status, contract address, chain, ref, recipient, amount and payer, and counts a receipt only if its block is the canonical block at that height | SDK e2e (incl. stale-receipt test) |
| Recovered payments are real | `findPayments` re-checks each log's contract address, `orderRef`, recipient and fields client-side, so an RPC that ignores the filters cannot inject other contracts' events | SDK e2e (misbehaving-RPC test) |
| One payment settles one share | FairEats stores `(chain_id, tx_hash, log_index)` under a UNIQUE constraint, settles one share at a time, and re-checks the amount owed inside the write transaction | `apps/faireats/test/server.test.ts` race tests |
| Client's view of the tree is honest | `fetchGroup`: rebuilt root must equal the on-chain root at the same block. `groupFromCommitments`: rebuilt root must be in the pool's `knownRoots` | `GROUP_MISMATCH` |
| A stored note cannot be guessable | `parseNote` accepts only a key that is base64 of exactly 32 bytes; Semaphore's `Identity.import` would otherwise derive a valid, public identity from `""` or a truncated key | SDK e2e |
| Batched deposits are the pool's own deposits | `FairPoolBatcher.depositMany` calls `FairPool.deposit` once per commitment, so the tree, the Deposit events, the cap and the pause are the pool's. It pulls only from `msg.sender`, checks the amount received by balance delta, approves the pool for exactly the batch and resets the allowance, and reverts unless its own balance ends where it started. All or nothing: one bad commitment reverts the batch | `FairPoolBatcher.test.ts` (incl. spending a batched note with a proof) |
| The relayer cannot be made to waste gas on duplicates | Proof fields must be canonical decimal uint256 (no leading zeros), so one nullifier has one in-flight key; every request is simulated before sending | SDK e2e |

## Trust assumptions

- **Owner** of `FairPay` and `FairPool` can pause either contract for as long as it likes, change the deposit cap, and change the merchant allowlist. It can also call `renounceOwnership()` (inherited from OpenZeppelin `Ownable`). Pausing `FairPool` stops deposits and `pay`, and pausing `FairPay` or delisting every merchant stops payments, but none of these stops `FairPool.withdraw`: a note's owner can always take its 5 USDC back to a wallet of their choice. The owner cannot move funds. Use a Safe and treat the owner key as able to stop payments.
- **FairPoolBatcher** (`packages/contracts/contracts/FairPoolBatcher.sol`) has no owner, no storage and no admin functions; its pool and token are immutable, read from the pool when it was deployed. Users approve it (the exact total, only when the allowance is short), so its address is trusted like the pool's: the app gets both from the server's `/api/config`, and the SDK refuses a batcher whose `pool()` or `token()` differs from the deployment. An allowance given to it can only be spent by the same wallet's own `depositMany`. Tokens sent to it directly are stuck for good (there is no rescue function, because that would need an owner). A front-runner who copies a commitment from a pending batch makes the batch revert, and pays for a note only the victim can spend. A batch fills the deposit cap faster: 20 notes per call.
- **EIP-5792 batches.** When a browser wallet reports atomic batching as `supported` on Monad testnet, the app sends the approval and the deposits as one `wallet_sendCalls` with `atomicRequired`. The wallet then executes them; a wallet that reports `ready` (it would first upgrade the account to a smart account) is not asked, and gets separate transactions.
- **Relayer** can censor (refuse to submit) but cannot steal or redirect. Users can submit `pay()` themselves at the cost of linking their gas wallet. If a third party front-runs the relayer with the same proof, the payment still succeeds but the relayer reports `RELAYER_REJECTED`; `findPayments` recovers it.
- **FairEats server** (`apps/faireats`, the standalone restaurant demo) runs the relayer and the deposit indexer, and is the party that decides an order is paid. Browsers do not trust its commitment list (the root is checked on-chain) and it cannot spend notes, but it sees request metadata: see Known limitations.
- **FairPay app server** plays the same role for its bills and restaurant orders: it runs the relayer and the deposit indexer, decides a share is paid, and sees request metadata. It also holds every account's data (profiles, friends, bills, orders, invoices) in its database. See [FairPay app server controls](#fairpay-app-server-controls).
- **Semaphore verifier and circuits** are Semaphore v4.14.5 (audited upstream). `MonadSemaphoreVerifier` is the upstream verifier with one change: it forwards `gas()` to the BN254 precompiles instead of fixed amounts (200 / 8,000 / 241,333). Monad prices these precompiles higher (ecMul measured at ~30,000 gas), so the stock verifier runs out of gas and returns `false` for every proof. Precompiles are fixed-cost and cannot re-enter, so forwarding all gas is safe; if a precompile still runs out of gas the check returns `false`, `pay` reverts, and no nullifier is used up. The deploy script verifies a real proof on the target chain before deploying the pool. Proof artifacts are fetched at runtime from `snark-artifacts.pse.dev` by `@zk-kit/artifacts`; for production, self-host and pin their hashes.
- **RPC** is assumed available, not honest: tree reconstruction is checked against on-chain roots, `findPayments` re-filters logs, and `verifyPaymentTx` rejects receipts from non-canonical blocks. A dishonest RPC can still withhold data (payments stay `pending`, private payments fail with `GROUP_MISMATCH`) and sees the IP and every request of whoever uses it.

## FairEats server controls

Details are in [apps/faireats/README.md](apps/faireats/README.md). In short:

- Prices, shares and `orderRef`s are created on the server. The browser sends item ids and quantities, and later only a transaction hash; every fact used to mark a share paid comes from the chain.
- The relayer endpoint only spends gas for an open share at this restaurant's merchant address that still owes at least one note after counting relays already in flight, at most 4 relays at a time and 12 per minute per client address. The server credits the relayed payment itself before releasing the share.
- The deposit indexer only serves deposits with `INDEXER_CONFIRMATIONS` (default 2) blocks on top, replaces deposits a reorg rewrote, and rescans when its count disagrees with the pool's `depositCount`.
- Kitchen endpoints need a PIN of at least 6 characters, compared in constant time. Only wrong PINs count against the limit: 10 per 15 minutes per client address and 60 per hour overall.
- `POST /api/*` requires `Content-Type: application/json` (blocks simple cross-site posts), bodies are capped at 16 KB, and responses carry a strict Content-Security-Policy, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer`.
- Relayer, RPC and SDK error text is logged on the server and replaced with fixed messages for clients, because raw errors can contain node URLs and the relayer's address and balance.
- Rate limits are in memory, per process. Behind a reverse proxy set `TRUST_PROXY_HOPS` to the exact number of proxies; a higher number lets clients choose their own rate-limit key.

## FairPay app server controls

The FairPay app (`apps/fairpay`) is the main app: bills between friends, plus Business > FairEats (restaurants, menus, tables, orders, GST invoices). The server code is in `apps/fairpay/server`; tests are in `apps/fairpay/test`. In short:

- **Sign-in with Ethereum (EIP-4361).** `GET /api/auth/nonce` hands out a random nonce that is single use and expires after 10 minutes. `POST /api/auth/verify` accepts a message only if its domain, scheme and URI match `PUBLIC_ORIGIN` exactly, it names Monad Testnet's chain id, it was issued in the last 10 minutes, and it carries an unused nonce. The nonce is used up before the signature is checked, so one message can only be tried once. An ordinary wallet signature is recovered locally; a smart wallet is checked on-chain (ERC-1271 / ERC-6492). Both endpoints allow 30 requests a minute per client address (`server/auth.ts`).
- **Sessions.** A successful sign-in sets the `fp_session` cookie: 32 random bytes, `HttpOnly`, `SameSite=Lax`, `Secure` when `PUBLIC_ORIGIN` is `https://`, valid for 7 days. The database stores only the token's SHA-256, so a database leak does not leak sessions. Signing out deletes it.
- **CSRF.** Every `POST`, `PUT`, `PATCH` and `DELETE` to `/api/*` must carry the header `x-fairpay: 1` or gets a 403 (`server/http.ts`). A custom header forces a CORS preflight, and this server never approves one, so another site can't send it. Unlike FairEats, the `Content-Type` is not checked; bodies are parsed as strict JSON objects instead.
- **Database.** Data is in Postgres: Supabase in the cloud, a local PGlite otherwise. Row level security is enabled on every table with no policies (`server/schema.sql`), so Supabase's public API (its anon and authenticated keys) can read or write nothing. Only the FairPay server, connecting with `DATABASE_URL` as the database owner, can. Anyone who has `DATABASE_URL` has all the data: treat it like a key. The connection uses TLS and verifies the database's certificate and host name; Supabase's certificates are signed by its own CA, which the server gets from `DATABASE_CA` and without which it refuses to start (`server/db.ts`, DEPLOY.md).
- **Payments are verified on the server.** The browser sends only a transaction hash (`POST /api/pay/:kind/:id/settle`). The server checks it on-chain with `verifyPaymentTx` against the share's own `orderRef`, recipient, amount and, when a seat is bound to a wallet, that payer (`server/routes/pay.ts`). A public payment must be exactly what is due; a confidential one exactly one note. The server then re-reads the share and its bill or order under row locks, stores the payment under `UNIQUE(chain_id, tx_hash, log_index)`, and credits it in the same database transaction. The `payments` table is append-only (a trigger refuses updates and deletes). A payment is only credited after 2 confirmations (see Known limitations). An order's payout wallet is fixed when the order is placed, so changing it mid-order doesn't strand guests who already paid the old one. Money that arrives but can't be credited (a share already paid, a closed bill or order, a payment larger than what was left, or a public payment from a wallet other than the seat's) is still checked on-chain; if it is a real payment for that share, the recipient (the bill's recipient or the restaurant owner) gets an activity note to refund it, and for a cancelled order the owner gets the refund note.
- **Payout wallets.** A restaurant's payout wallet can only be set to the wallet its owner is signed in with, so nobody can point a restaurant at another business's allowlisted wallet to show "Private payments".
- **Relayer and faucet.** As in FairEats, the relayer only spends gas for an open share whose recipient is allowlisted on the pool and that still owes at least one note after counting relays in flight: at most 4 relays at a time and 12 per minute per client address. The faucet allows 3 claims an hour per client address, one per wallet every 30 minutes, and 60 an hour overall. Relayer and RPC error text stays in the server log; clients get fixed messages. A relayed note whose payment the server could lose track of is looked for again: if the receipt wait times out the server answers with the transaction's hash and settles it like any relayed payment; if the relay failed because the note was already spent, its transaction reverted, or the outcome is unclear, the server lists FairPay payments for that `orderRef` and merchant in the last 2,000 blocks (`findPayments`) and settles each through the normal verification (`server/routes/chain.ts`). It looks right away, and again after the grace period when the outcome was unclear or the receipt timed out. `UNIQUE(chain_id, tx_hash, log_index)` keeps a payment from counting twice.
- **Ids and links.** Ids are random (80 bits), never sequential. Bill, payment and order pages answer a missing id and one you may not see with the same 404. Links carry separate random tokens of 32 bytes each:
  - A bill's **share token** (`/b/...`) lets the holder see the bill and pay its shares; a signed-in holder can also claim a name-only seat that still owes and has nothing paid. The bill's creator can free a claimed seat that has no payment, so a wrong claim can be undone. A share's `orderRef` (which finds its payments, and so public payers' wallets, on-chain) goes only to someone who may pay it now.
  - An order's **share token** (`/o/...?t=...`) lets the holder see the order and pay its shares.
  - An order's **invoice token** (`/i/...`) only reads the GST invoice. It can't pay, and the share token never opens the invoice. It names no payer: public transactions (which show the payer's wallet) are listed only for the restaurant's staff and the wallet that placed the order, never for a share that also had a confidential payment, and a confidential payment never names its guest.
- **Ordering without signing in.** Placing an order holds a table, so one client address may place 6 orders per 10 minutes and hold at most 2 unpaid orders per restaurant (a signed-in wallet: 2 of its own), and an order with nothing paid gives its table back after 15 minutes.
- **Image uploads.** Only a restaurant's owner or manager can upload. The type comes from the file's first bytes, never from the client's `Content-Type`: only PNG, JPEG and WebP are accepted, never SVG. Uploads are capped at 1 MB while they are read, at 1,000 images and 25 MB per restaurant, and at 30 new images an hour per wallet and 60 per client address. Images are served with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'`, so even a polyglot file can't run as a page (`server/routes/images.ts`).
- **Headers.** Responses carry a Content-Security-Policy (scripts only from the app itself, plus `wasm-unsafe-eval` for the prover), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `nosniff`, and HSTS when served over `https://`. API responses are not cached. On the public website the app's pages are served by Vercel at `/pay/` with the same policy (`apps/site/vercel.json`), and the rest of the site keeps its stricter one.
- **Served through the website.** The website proxies `/api/*` to the server (DEPLOY.md, "The website serves the app"), so the session cookie, CSRF header and sign-in all live on the website's origin, which is `PUBLIC_ORIGIN`. The server's own address then redirects page visits to the website. Behind Vercel, Cloudflare and Render's load balancer, set `TRUST_PROXY_HOPS=4`; `GET /api/whoami` shows a caller the address their rate limits use. With the optional `PROXY_SECRET`, a request that skipped Vercel is recognised (no `x-fairpay-proxy` header, compared in constant time) and its address is read one hop further right, where Render wrote it, so it can't choose its own.
- **What a confidential payment hides.** It hides which wallet paid, not the amount: the amount is a whole number of fixed-size notes and is public on-chain. The restaurant owner's notifications for a confidential payment name neither the wallet nor the guest's seat. Bills between friends are always paid publicly, because the pool only pays allowlisted businesses.
- **The owner's money view.** `GET /api/restaurants/:id/money` (totals, payout wallet, "needs attention"), `/money/payments` (the log), `/money/payments.csv`, `/money/invoices` and `POST /money/payments/:paymentId/recheck` (re-runs `verifyPaymentTx` for a stored payment) answer only the restaurant's owner; everyone else gets the same 404 as an unknown id (`server/routes/money.ts`). A confidential payment never returns its payer or its guest's seat. A share paid partly in public and partly confidentially returns no transaction, block, log index, `orderRef` or payer for any of its payments, since the confidential transaction's `orderRef` would find the public one on-chain. Otherwise the owner sees each transaction that paid their own wallet: a confidential one names FairPool as payer and the relayer as sender. The re-check allows 20 a minute per client address and per wallet, the CSV export 10 a minute per wallet, and CSV cells that a spreadsheet would run as a formula get a leading apostrophe. Exception to "Ids are random": the log pages by the `payments` table's sequential id, so an owner can roughly estimate how many payments the whole platform has had.
- **Dashboard stats.** `GET /api/restaurants/:id/stats?range=today|7d|30d|mtd` (revenue, orders, covers, top dishes, busy hours, turnover, cancellations) answers any of the restaurant's staff, the same people who read its orders list, with the same answers (401 signed out, 403 not staff, 404 unknown id). Its `money` field (public and confidential amounts, tips) comes from the payments table and is filled in for the owner only, null for everyone else, as in the money view (`server/routes/stats.ts`).
- **Team pay (owner pays staff).** The owner pays a staff member straight from their own wallet with one ERC-20 `transfer` of the deployment's USDC; no FairPay contract holds the money. The browser then sends the transaction hash with the staff wallet, amount and an optional note (`POST /api/restaurants/:id/team-pay`). The server records nothing it hasn't checked on-chain (`server/transfers.ts`): the transaction succeeded, its block is canonical and has the payments' confirmations (2 on Monad testnet; until then 202 "pending" and the browser asks again), and it holds exactly one `Transfer` log from the deployment's token contract (Transfers from other contracts are ignored; two or more of the token are refused), with `from` the restaurant owner's wallet, `to` a wallet on this restaurant's staff (checked again under a row lock when it is stored) and `value` exactly the amount. It is stored once under `UNIQUE(chain_id, tx_hash, log_index)` in the append-only `team_payouts` table; the same request again gets the same payout back, any other claim on that transaction is refused. The staff member gets an activity note. Every `/team-pay` endpoint (view, `/payouts`, `/payouts.csv`, the POST) answers only the owner, with the same 404 as an unknown id for everyone else; `/team-pay/mine` lists a staff member's own payouts from that restaurant (current staff, or anyone it has paid). The POST allows 60 a minute per client address and per wallet, the CSV 10 a minute per wallet. These are public transfers: the owner's wallet, the staff wallet and the amount are on-chain, and the UI says so. The note stays in FairPay. A sent payout is remembered in the browser until the server records or refuses it, so a reload checks it again instead of paying twice.
- **Team pay escrow (FairPayroll).** Only when `deployments/<network>.json` records `payroll` (written by `packages/contracts/scripts/deploy-payroll.ts`); without it every escrow endpoint answers 503 "not set up" and the app keeps its "coming soon" card. The escrow belongs to the restaurant owner's wallet (the contract's employer), so restaurants with the same owner share one escrow. The contract has no owner, admin, pause or upgrade; what it guarantees, from its own notes: only the employer moves its free funds (`withdraw`, `approveShifts`, a back-dated `setSchedule`); money owed to staff is never withdrawable, because reservations up to now are made first and approved shift pay is set aside in full when approved; schedules pay completed periods, and ending or changing one (or an employee's `resign`) settles the period in progress pro rata for the time worked; when the escrow is short, ended schedules' unfunded pay becomes debt that new funding pays first, shared pro rata between debtors, before any running schedule; `claim` and `claimFor` pay only the employee. Salaries, shift pay and claims are public on-chain (who pays whom, how much, how often), and the UI says so.
  - *What FairPay's server does.* It never holds or moves escrow money. The owner's browser funds (an exact approval, never unlimited), withdraws, approves shifts and sets or ends schedules; staff claim or resign from their own wallets. The server reads `employerInfo`, `employeeInfo`, `scheduleOf` and `fundingNeeded` at one block and never takes chain state from the browser (`server/routes/payroll.ts`). The one thing it records from a transaction hash is a shift approval (`POST /api/restaurants/:id/team-pay/shifts/approve`): only after the transaction succeeded in a canonical block with the payments' confirmations (2 on Monad testnet; until then 202) and its `ShiftApproved` events come from the payroll contract itself with the restaurant owner as employer; a pending shift is marked approved only when shiftId, employee and amount all match. Shift ids are keccak256 of a random server id, unique per (chain, contract, employer). An event indexer (`server/payroll.ts`) copies every FairPayroll event from confirmed blocks into the append-only `payroll_events` (UNIQUE per log; progress in `payroll_indexer_state`, starting at `payrollDeployBlock`), and marks a matching pending shift approved the same way, so a lost browser still ends up recorded. It stores every employer's events, not only owners': anyone can add events to a public contract, each costing them gas. A deep reorg beyond the confirmations would leave stale rows in the history; the escrow numbers themselves are always read live.
  - *Who can use it.* Every owner endpoint (`/team-pay/escrow`, `/escrow/history`, `/shifts`, `/shifts/:id`, `/shifts/approve`, `/members/:wallet`) answers only the restaurant's owner, with the same 404 as an unknown id for everyone else. `/team-pay/escrow/mine` (and `/mine/history`) shows a staff member only their own position, schedule, shifts and events, for current staff or anyone with escrow shifts or events from that owner. Views allow 60 a minute per wallet (each costs several RPC reads), shift changes 120, approvals 60 per wallet and per client address. Chain read errors are logged in one line; clients get a fixed sentence.
  - *Auto-pay keeper.* Off unless `KEEPER_KEY` is set, and only with a payroll contract. The server refuses to start when `KEEPER_KEY` equals `RELAYER_KEY` or `FAUCET_KEY`. Every 5 minutes (the first run waits one interval) it calls `claimFor(owner, staff)` from its own wallet, only for staff whose owner turned auto-pay on in `payroll_settings`, who are still on that restaurant's staff, and whose `employeeInfo.claimable` is above 0. `claimFor` pays only the employee, so the keeper's key can't move anyone's money anywhere else; at worst it spends its own gas. It sends at most 10 claims a run and 60 an hour, one per pair an hour, simulates each first, and pauses while its MON can't cover a claim's gas reservation. Logs carry short wallets, amounts and transaction hashes, never keys. The keeper's address is public in `/api/config` and in each `Claimed` event's `caller`, which the history shows as "Auto-pay".
- **Configuration.** In production (`NODE_ENV=production`, set by `apps/fairpay/Dockerfile`) the server refuses to start without `DATABASE_URL` and a valid `PUBLIC_ORIGIN` (`server/env.ts`, `server/origin.ts`). In any mode it refuses to start when `RELAYER_KEY` and `FAUCET_KEY` are the same key, since the relayer and the faucet would pick the same nonces, and likewise when the optional `KEEPER_KEY` equals either (`server/chain.ts`, `server/payroll.ts`). Behind a reverse proxy set `TRUST_PROXY_HOPS` to the exact number of proxies, as for FairEats.

## Known limitations

- **Small anonymity set.** A private payment hides the payer only among the deposits in the tree its proof used. On a demo pool that can be a handful of people. The contract accepts any historical root, so a proof built on an older tree has the smaller anonymity set of that tree. Say the number honestly in demos.
- **The restaurant can shrink it further.** `groupFromCommitments` accepts any prefix of the deposit list whose root the pool has recorded. A malicious FairEats server could serve each browser a prefix of a different length and see which root a payment uses, linking that payment to a browser session. Requiring the full current list would break payments whenever the indexer lags, so this is left to the operator to decide.
- **Timing and amount correlation.** Depositing and paying in quick succession, or paying a 15 USDC share with three notes, can link them. FairEats submits the notes for one share back to back, so a multi-note share shows up as several pool payments for the same `orderRef` within seconds. Top up well before paying.
- **Network metadata.** The FairEats server sees the client IP on faucet requests (which carry the wallet address) and on relay requests (which carry the `orderRef`). The RPC provider sees the IP behind deposits and proof-time reads. Either can correlate wallets with private payments from the same browser or network.
- **Notes live in browser storage.** FairEats keeps notes in `localStorage` for the app's origin. Clearing site data loses them (and the deposits) unless the user exported a backup. Any script running on that origin, a malicious browser extension, or anyone with access to the device can read and spend them. The backup file is equally sensitive.
- **Demo wallet key in browser storage.** The FairEats demo wallet's private key is also in `localStorage`. It is for testnet only and must never hold real funds.
- **Batched deposits link their notes.** Notes added in one `depositMany` (or one top-up) are visibly from the same wallet at the same moment, exactly like the separate deposits they replace. Spending them in quick succession links them further.
- **Fixed denomination.** Shares must be multiples of the note size (5 USDC). No change notes.
- **Withdrawals make the pool a mixer.** `withdraw` lets a note go to any address, not only allowlisted merchants, so the pool can now move funds between unlinked wallets (5 USDC per note, within the anonymity set). This is the trade-off for never freezing users' money. There is no association-set or compliance check on withdrawals; that is roadmap. A withdrawal's recipient is public, and withdrawing to the wallet that deposited links the two.
- **Notes are bearer secrets.** Losing one loses the deposit; leaking one lets anyone spend it.
- **Confirmations.** `verifyPaymentTx` defaults to 1 confirmation and FairEats uses that default. The FairPay app waits for 2 on Monad testnet (`PAYMENT_CONFIRMATIONS`, counting the payment's own block; 0 on a local Hardhat chain): until then settle answers "pending" (202) and the browser asks again. The canonical-block check catches a receipt whose block was replaced, but neither is a substitute for waiting for finality. Raise it for anything of value.
- **Relayer retries.** If waiting for a receipt times out after the relayer sent a transaction, the nullifier is released; a retry can then send a duplicate that reverts and costs the relayer gas.
- **Single-process state.** FairEats rate limits, relay holds and per-share locks live in one process. Running several server instances would need a shared store. The FairPay app is the same: its rate limits, relay holds and faucet claims are in memory. Its database row locks do cover several processes when it credits a payment.
- **FairPay app: keys and notes in browser storage.** The FairPay app's test wallet keeps its private key in `localStorage` (`fairpay.testWalletKey`), and confidential-payment notes are in `localStorage` too (`fairpay.notes.<chain>.<pool>`). The same risks as FairEats apply: clearing site data loses the notes, and any script on the origin, a malicious extension or anyone with the device can read and spend them. Testnet only.
- **Shared wallets between servers.** Each server keeps a wallet's transactions in order only inside its own process: the SDK queues the relayer's sends per account (`sendSimulated` in `packages/sdk/src/chain.ts`) and each faucet has its own queue. If the FairEats server and the FairPay app send from the same relayer or faucet wallet, their transactions can pick the same nonce and one of them fails. Give each server its own wallets (see DEPLOY.md).
- **FairPay app: known gaps from the audit, not fixed yet.**
  - *Spam (L7):* bills, staff invitations and new restaurants can name any wallet and put attacker-written text in its activity feed; limits are per wallet only, and the directory shows only the newest 200 restaurants.
  - *Deposit cap (L8, testnet):* MockUSDC's `mint` is open to anyone, so the pool's deposit cap (default 200) can be filled with junk deposits, which turns private payments off until the owner raises it.
  - *Faucet drain (L9, testnet):* a few addresses can use the faucet's 60 claims an hour, leaving nothing for real users until the hour is over.
  - *Relayer gas griefing (L10):* someone who submits their own proof straight to the pool while the relayer sends the same one makes the relayer's transaction revert and pay gas; bounded by the relay limits.
  - *Visitors can choose their rate-limit address (S1):* through the website the FairPay service needs `TRUST_PROXY_HOPS=4` (Vercel, Cloudflare, Render's load balancer). Vercel's external rewrite keeps a client's own `X-Forwarded-For`, so a visitor who sends one can pick their per-address rate-limit key; with `3`, every visitor would share Vercel's addresses instead. Global caps still hold (faucet 60 claims an hour, 4 relays at a time). Fix to do: read Vercel's own client-address header, and trust it only on requests carrying the proxy secret.
- **Upstream advisory.** `npm audit` reports `snarkjs@0.5.0` inside `circom_tester`, a build-time tool pulled in by `@zk-kit/artifacts`. It is not on the proof generation path. `ws` and `underscore` are overridden to patched versions.
